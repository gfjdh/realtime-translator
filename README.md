# 英文游戏实时翻译悬浮窗

抓取游戏窗口里的一块画面，用 OCR 把英文读出来，机翻成中文，显示在一个置顶的小窗里。
全程离线识别（模型随包附带），只有翻译那一步需要联网。

```
抓帧(按窗口) → 画面变化检测 → RapidOCR → 文本稳定判定 → 翻译 → 置顶悬浮窗
```


---

## 环境要求

- Windows 10 1903+ / 11（Windows Graphics Capture 的下限；更老的版本会自动退回
  Desktop Duplication，见 `--backend`）
- Python 3.10+（在 3.13.7 上实测通过）
- 磁盘约 200MB：`opencv-python` 44MB + `onnxruntime` + `rapidocr` 自带的 27MB 模型

## 安装

```bat
setup.bat
```

它建一个 `.venv` 并把依赖装进去。之后所有命令都用 `.venv\Scripts\python.exe` 跑。
想装进全局环境也行：`pip install -r requirements.txt`。

## 三步上手

### 1. 找到游戏窗口

```bat
.venv\Scripts\python.exe main.py --list
```

打印当前所有可见窗口，格式是 `标题  [exe名]`：

```
Fantasy Maiden Wars - Dream of the Stray Dreamer -  [fmw_dosd.exe]
```

`-w` 既可以给标题的一部分，**也可以直接给 exe 名**，两者都试：

```bat
main.py -w name              rem 同一个游戏，用 exe 名一样能匹配
```

用 exe 名通常更省事——窗口标题会带一堆后缀、会变，有时甚至是空的。
匹配优先级是 标题全等 → exe 全等 → 标题子串 → exe 子串，前面命中了就不看后面，
所以输入 `steam` 不会一下子匹配到一堆 helper 进程。

### 2. 校准抓取范围（**这步别跳过**）

默认抓整个客户区，会把血条、小地图、技能栏一起 OCR 进去，既慢又容易出垃圾文本。
先看看实际抓到的是什么：

```bat
.venv\Scripts\python.exe main.py -w "游戏名" --snapshot crop.png
```

打开 `crop.png`，它就是你将要 OCR 的那块画面。如果里面混了别的东西，就调 `--region`
把范围缩小到只剩对话框。`--region` 是相对客户区的比例：

```bat
rem 只要中间偏下的一条横带
.venv\Scripts\python.exe main.py -w "游戏名" --region 0.05,0.60,0.95,0.88 --snapshot crop.png
```

反复调到 `crop.png` 里正好是你要翻译的文字为止。

### 3. 启动

```bat
.venv\Scripts\python.exe main.py -w "游戏名" --region 0.05,0.60,0.95,0.88
```

不加 `--region` 就抓整个客户区。窗口右下角可以拖拽改大小，顶栏可以拖动位置。
参数调顺了之后加 `--save-config` 存进 `config.json`，下次直接 `main.py` 就行。

## 热键

| 热键 | 作用 |
|---|---|
| `Ctrl+Alt+F9` | 暂停 / 继续 |
| `Ctrl+Alt+F10` | 鼠标穿透开关（开着的时候鼠标点不到悬浮窗） |
| `Ctrl+Alt+F11` | 退出 |

默认用功能键而不是字母键，是因为实测这台机器上 `ctrl+alt+t/c/x/z/s` 全被别的工具占着，
`RegisterHotKey` 会直接失败——热键按了没反应，还很难查。换别的组合改 `config.json`
里的 `hotkey_*` 字段即可。

注册失败时窗口上会显式提示，不会静默失效。

悬浮窗本身也支持右键菜单（暂停、清空、显示原文开关、鼠标穿透、退出），
`Ctrl+C` 复制全部内容。

## 常用参数

| 参数 | 说明 |
|---|---|
| `-w, --window` | 目标窗口标题的一部分，大小写不敏感 |
| `--region x0,y0,x1,y1` | 只抓客户区的一块，比例形式。**强烈建议设置** |
| `--snapshot 路径` | 把抓取范围存成 PNG 后退出，用来校准选区 |
| `--once` | 抓一帧做 OCR + 翻译并打印，不开窗口，用来快速验证 |
| `--list` | 列出可见窗口 |
| `--fps` | 抓帧频率上限，默认 6。画面没变时不会跑 OCR，所以不用调大 |
| `--det-size` | OCR 检测长边上限，默认 1280。字小认不出来就调到 1600~1920 |
| `--min-score` | OCR 置信度下限，默认 0.5。出垃圾文本就调高 |
| `--backend` | `auto`（默认）/ `wgc` / `dxcam` / `mss`，`auto` 按此顺序依次尝试 |
| `--output` | 抓帧用的显示器序号，默认自动跟随窗口所在屏 |
| `--alpha` `--width` `--height` `--font-size` | 悬浮窗外观 |
| `--no-cache` | 不读写磁盘翻译缓存 |
| `--save-config` | 把本次参数写入 `config.json` |
| `--debug` | 状态栏显示 OCR 耗时和抓取尺寸 |

## 工作原理

**抓帧后端怎么选**：`auto` 按 `wgc → dxcam → mss` 依次尝试，谁先能起来用谁。
前两个抓的是合成后的桌面画面，窗口被盖住就会抓到遮挡物的内容；wgc 按窗口句柄
抓窗口自己的内容，盖不盖住都一样，所以默认走它。

wgc 拿到的是窗口的**可见边框**（DWM 的 extended frame bounds），不是客户区，
所以代码里减掉了两者的偏移再裁一刀 —— 实测这样裁出来的画面和 dxcam 抓客户区
**逐像素完全相同**（1125x375，平均差 0.00/255）。这件事很重要：它意味着
`--region` 的比例在各个后端之间是同一套含义，换后端不用重新校准选区。

**为什么快**：三处设计。

1. `dxcam` 的 `grab()` 在画面没有新帧时直接返回 `None`，于是静止的对话框不会触发
   任何 OCR。挂机时 CPU 几乎为零。wgc 只在画面变化时才回调，但它照样会在背景
   有动画时一直出帧，所以又加了一道下采样指纹过滤，让三个后端行为一致。
2. `Det.limit_type` 从默认的 `min` 改成 `max`。默认配置会把 720×150 的对话条按**短边**
   放大到 736，实际送进检测模型的张量是 3500×736，单帧 630ms。改成限制长边后是 92ms，
   识别结果完全一致——**快了近 7 倍**。
3. 关掉了文本方向分类（`use_cls`）。那个模型是用来判断文字有没有倒转 180° 的，
   游戏对话永远是横排，纯属浪费。

**文本稳定判定**：OCR 出结果后不会立刻翻译。只有连续两次识别到同一段文本（或者画面
连续若干帧没变化）才认为这段话"读完了"，然后才送去翻译。这样逐字打印的动画不会
把半截句子翻出来。

**翻译降级链**：先用 Google 的免费端点（`translate_a/single`，质量最好也最快），
失败则自动降级到 MyMemory。上次成功的那个会被记住，下次优先用，省掉一次注定失败的请求。
两个端点都失败时错误会显示在窗口里，下一句会自动重试。

**缓存**：内存 + 磁盘两层（`cache/translations.json`，上限 5000 条）。游戏里同一句
台词会反复出现，缓存能同时省掉流量和几百毫秒的延迟。

## 已知限制

**1. 独占全屏（Exclusive Fullscreen）抓不到。**
独占全屏时桌面合成被绕过，三条抓帧路径都拿不到画面。请在游戏里把显示模式改成
**无边框窗口**（Borderless Windowed）或窗口化。

**2. 最小化的窗口抓不到。**
窗口最小化后不再渲染，wgc 也就没有帧可给。这不是错误，只是没内容 —— 把窗口
还原即可。窗口被别的程序盖住则**完全不受影响**。

**3. 用 `dxcam`/`mss` 时，被遮挡的窗口抓到的是遮挡物的内容。**
这两个后端抓的是**合成后的桌面画面**，不是窗口自己的缓冲区。默认的 wgc 没有这个
问题；只有 wgc 起不来、退到这两个后端时才会遇到。

这时启动会自动检查并明确报警，不会让你对着一堆莫名其妙的译文发呆：

```
警告: 目标窗口被「xxx - Microsoft Edge」盖住了，现在抓到的会是它的内容。
      请把游戏切到前台再启动；如果游戏是独占全屏，改成无边框窗口。
```

检测方式是在窗口中心点问一句"这个位置最顶层是谁"，比截屏比对便宜得多。
窗口正常在最前面时不会误报，用 wgc 时也不会报（那对它是误报）。

**4. 翻译依赖第三方免费接口，不保证一直可用。**
Google 的免费端点在不少网络环境会返回 429/403（开发这台机器上四个 Google 端点全部被挡），
这时会自动走 MyMemory。MyMemory 的限制：单次查询**最多 500 字符**（超了报错，代码里
按 480 切块），且有每日免费额度，用尽当天会提示。

**5. 识别率取决于游戏字体。**
PP-OCR 对规整的印刷体最准。艺术字、强描边、低对比度、动态模糊的字体识别率会下降，
这也是选它而不是 Windows 自带 OCR 的原因。调 `--det-size` 和 `--min-score` 通常能改善。

**6. 没有做文本与非文本的区分。**
选区里如果是纯背景（没有文字），OCR 返回空，不会有输出，这是正常的。

## 故障排查

| 现象 | 原因 / 处理 |
|---|---|
| `没找到匹配 xxx 的窗口` | 先跑 `--list` 看确切标题和 exe 名；窗口最小化时枚举不到 |
| 游戏在运行但 `--list` 里没有 | 窗口最小化了。最小化的窗口没有可见窗口句柄，先把它还原 |
| 窗口一片空白，什么都没显示 | 先跑 `--once` 看能不能识别出文本；再用 `--snapshot` 确认选区里真的有字 |
| OCR 读到一堆乱码 | 选区混进了 HUD。用 `--region` 缩小范围 |
| 抓到的是别的程序的内容 | 退到 `dxcam`/`mss` 了，游戏窗口被盖住，见"已知限制 3" |
| `wgc 不可用（…）` 后自动换了后端 | 系统低于 Win10 1903，或 `windows-capture` 没装上。功能不受影响，只是别让游戏窗口被盖住 |
| 窗口还原后仍一直抓不到画面 | 窗口最小化过。wgc 需要窗口在渲染，还原即可 |
| 热键没反应 | 组合被别的程序占了。窗口上会提示，换 `config.json` 里的 `hotkey_*` |
| 翻译一直失败 | 免费接口被限流或额度用尽，换个网络或等一会儿 |
| 抓帧初始化失败 | 试试 `--backend mss`；双显卡机器可能需要 `--output` 指定显示器 |
| 文字位置整体偏移 | 高 DPI 缩放导致。程序已做 DPI 感知，若仍偏移请用 `--snapshot` 核对实际抓取范围 |

## 开发 / 验证

`.scratch/` 下有几个可以直接跑的验证脚本：

| 脚本 | 验证内容 |
|---|---|
| `e2e.py` | 起一个假游戏窗口，跑 `--list`/`--snapshot`/`--once`/GUI 全流程 |
| `test_occluded.py` | **遮挡下各后端的行为**：wgc 必须照常识别，dxcam 必须报警告 |
| `probe_occluded.py` | 一次性调查脚本：wgc 帧与 dxcam 客户区的逐像素比对（当年就是靠它定下坐标换算的） |
| `fake_game.py` | 那个假游戏窗口（深色底 + 白字对话框） |
| `overlay_smoke.py` | 悬浮窗显示逻辑：消息投递、原文开关、鼠标穿透、长跑裁剪 |
| `bench_ocr.py` | OCR 各参数组合的耗时对比 |
| `bench_translate.py` | 探测哪些免费翻译端点在当前网络可用 |

```bat
.venv\Scripts\python.exe .scratch\e2e.py
.venv\Scripts\python.exe .scratch\test_occluded.py
```

遮挡测试会自己起一块全屏纯色窗口盖住假游戏，不需要手动摆窗口，也不会碰你
桌面上已有的任何窗口。

## 文件结构

| 文件 | 职责 |
|---|---|
| `main.py` | CLI 与流水线编排（抓帧线程 / 翻译线程 / 热键线程） |
| `winapi.py` | Win32 的 ctypes 封装：DPI、窗口枚举、鼠标穿透、全局热键 |
| `capture.py` | 抓帧，wgc 主路径 + dxcam / mss 降级，三条路径共用同一套 `--region` 语义 |
| `ocr.py` | RapidOCR 封装，按阅读顺序把识别框拼成文本 |
| `translate.py` | 翻译降级链 + 两层缓存 |
| `overlay.py` | tkinter 置顶悬浮窗 |
| `config.py` | 参数定义与 `config.json` 读写 |
